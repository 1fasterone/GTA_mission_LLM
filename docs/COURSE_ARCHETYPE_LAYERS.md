# Course archetype layers — a plan, fully landed

Status: **all five steps of the migration path are done.**
`schema.world_spec.course.zones` is real, live schema content that **all
five** archetype interpreters consume: ArenaPlane's path-route corridor
(arc-length axis, elevation), BoundedVolume (altitude-tier axis, elevation),
VerticalCorridor (drop-band axis, elevation — including the
submerged/water-dweller branch), VerticalSurface (climb axis, hazard height —
never the hold chain itself, to protect the reachability invariant), and
UISurface (reading-order axis, row z-depth — the one interpreter with no
natural "height" to make amplitude a fraction of, so it's raw depth units
instead — see each interpreter's own comment for why the axis differs). The
warning mechanism (`_ZONE_AWARE_ARCHETYPES`) stays in place for whatever
spatial primitive gets added next, so that one's own gap is loud too. Step 3's
prompt now asks the Pipeline LLM for zones on its own, content-gated section —
`zones` is populated by a real `unity-create` run now, not only by
hand-authored schemas or tests. Grounded in one working proof-of-concept
(`GENREOffRoadDesertRacing/Assets/Scripts/BajaLoopRoute.cs`, a hand-authored,
out-of-pipeline script — not generated by this compiler) that surfaced two
real bugs before any of this landed in the real compiler. See
[LAYOUT_ARCHETYPES.md](LAYOUT_ARCHETYPES.md) for the archetype system this
extends.

## The question that motivated this

A desert racing loop needs a whoop section, a dry lakebed, a rocky wash
crossing. If those are named enum values in the schema (`course_feature:
"whoop_section" | "dry_lakebed" | "wash_crossing"`), the compiler can only
ever emit a feature someone already thought to name — closed-world by
construction. The same compiler also needs to describe an underwater reef, a
falling-through-the-sky updraft corridor, or a cliff face's hold spacing.
Those aren't desert nouns, so a desert-shaped enum can't reach them.

## What proved out

`BajaLoopRoute.cs` replaced hardcoded `whoop`/`lakebed`/`wash`/`turn`
switch-branches with:

1. **One parametric axis.** `Sample(t)` / `Project(point)` — a point on (or
   near) the course, and its inverse, expressed as arc-length fraction `t ∈
   [0,1)` plus signed lateral offset from the centreline. This pair must be
   exact inverses of each other (verified numerically, round-trip error at
   float-epsilon across 20,000 random samples) — the bug that motivated
   double-checking this was a real one: the arc segments' original formula
   didn't geometrically connect to the straights they were supposed to join
   (a ~150 m gap at this course's scale), invisible in the terrain (which had
   its own, independently-correct distance math) but present in every AI
   waypoint baked from the broken parametrization.
2. **A small, medium-agnostic modifier vocabulary.** `enum TerrainModifier {
   Flat, Ripple, Dip, Rough }` — shape verbs, not desert nouns.
3. **Zones as ordered data**, not branches: `CorridorZone { startT, endT,
   modifier, amplitude, frequency, surfaceLayer }`. An interpreter
   (`DesertTerrainBuilder`) walks the zone list at every terrain point,
   summing every zone whose range contains that point's `t` (so a narrower
   zone layers additively on top of a wider one it's nested inside) and
   taking the last matching zone's `surfaceLayer` as authoritative.
4. **The whoop/wash relationship is nested, not sequential.** `RockyWash`'s
   `[startT,endT)` sits entirely inside `WhoopSection`'s — proving zones
   compose (a base feature + a narrower override) rather than needing to be
   mutually exclusive.

This is the concrete shape the rest of this plan generalizes.

## This pattern already exists, three times, unreconciled

`unity_layout_archetype.py` / `unity_layout.py` independently reinvented a
version of "slice a 1-D axis into zones" for three of its four spatial
primitives, each with its own name and its own rule:

| Archetype | The axis | The existing zoning |
| --- | --- | --- |
| `BoundedVolume` | altitude fraction of H | `_VOLUME_LAYERS` (3 altitude bands, `[0.2, 0.8]·H`), content round-robined across them |
| `VerticalCorridor` | drop height fraction | non-player content "stratified" across `[0.15, 0.85]·H`, never all at y=0 |
| `VerticalSurface` | climb height | hold chain built row by row; hazards placed "between hold rows," clear of holds by `_HAZARD_HOLD_CLEARANCE` |
| `ArenaPlane` (path-route variant) | arc-length along the route | *(none yet — this is what `BajaLoopRoute` adds)* |

None of these three share code or a data shape today. The proposal below is
**not** "teach terrain about zones" — terrain already needed zones and I
wrote them ad hoc. It's "notice this is the third or fourth time this exact
pattern was invented separately, and give it one name."

## The generalized primitive

```
RouteAxis:  Sample(t) -> (point, tangent)         -- t in [0,1) or [0,H] as fits the archetype
            Project(point) -> (t, lateralOrRadial) -- exact inverse of Sample

LayeredZone: { startT, endT, modifier: ModifierVerb, amplitude, frequency, layer }
             Contains(t) -> bool  (wrap-safe)

Evaluate(zones, t, ...) -> sum of every matching zone's contribution,
                           last matching zone's `layer` wins
```

`RouteAxis` is archetype-specific (a stadium loop's `t` is arc-length around
a closed curve; `VerticalCorridor`'s is linear height fraction; a cliff
face's could be arc-length up a spline draped on the wall). `LayeredZone` and
`Evaluate` are archetype-agnostic — the same struct and the same evaluator
regardless of what's being sliced.

### What the modifier verbs mean per medium

The verb is shared; its physical consequence is owned by the interpreter for
that archetype/medium, same as `DesertTerrainBuilder` today owns "Ripple
means elevation" for ground:

| Verb | Ground (ArenaPlane) | Water (BoundedVolume) | Air-fall (VerticalCorridor) | Cliff (VerticalSurface) |
| --- | --- | --- | --- | --- |
| `Flat` | dead-flat lakebed | still, current-free water | calm air, no drift | a ledge, evenly spaced holds |
| `Ripple` | whoop bumps | oscillating current | periodic wind gusts | evenly-spaced small holds |
| `Dip` | wash crossing (localized elevation drop) | a trench / thermocline pocket | a downdraft pocket | a stretch with no holds (a reach gap) |
| `Rough` | silt-flat noise | turbulence / visibility noise | unpredictable turbulence | loose/crumbling holds (slip chance) |

### Multi-layer composition — the two examples asked about

**Underwater with a rocky sea floor**: two zones covering (nearly) the same
`t`-range at different... this is where a single scalar `t`-axis per
archetype stops being enough — `BoundedVolume` already has this problem
today (its 3 altitude *layers* are a second axis, independent of position
along the swim path). The generalization needs **two independent axes** for
volumetric archetypes: `t` (along-path) and `depth` (below the water
surface/route). A "rocky sea floor" zone is authored on the *depth* axis (`depth
> 0.8·H`) with modifier `Rough`/`surfaceLayer=rock`, layered under an
along-path current zone authored on `t`. Two zones, two axes, same struct —
evaluated independently and composited (floor texture from the depth axis,
current strength from the `t` axis) rather than forced into one axis.

**A full dry lakebed course (the whole desert loop, not just one straight)**:
the trivial case — a `DesertZones`-equivalent list with exactly one entry,
`{ startT: 0, endT: 1, modifier: Flat, surfaceLayer: sand }`. Generality has
to include the boring case: an author who wants a monotonous course authors
one zone, not a workaround.

**Falling from the sky through a storm layer into calm air below**: zones on
the *height* axis of a `VerticalCorridor` — `{ 0.6·H, 1.0·H, Rough
(turbulence), ... }` above `{ 0.0·H, 0.6·H, Flat (calm), ... }` — same shape
as the underwater depth-axis example, different archetype.

**Hanging on a cliff with a crumbling section partway up**: zones on
`VerticalSurface`'s climb-height axis — a `Rough` zone (slip chance) nested
inside the overall hold-chain range, exactly mirroring `RockyWash` nested
inside `WhoopSection`.

So: **planar/path archetypes need one axis (`t`); volumetric and vertical
archetypes need two (`t` along the route/path, plus depth/altitude within
it)** wherever they don't collapse to a single line. `BoundedVolume`'s
existing 3-layer altitude split is already secretly this second axis with a
resolution of 3 — this plan would let it be an author-controlled zone list
instead of a fixed constant.

## Schema shape (IMPLEMENTED — `src/unity_schema.py`)

```python
class RouteZoneSpec(BaseModel):     # named *Spec to not collide with the
    start_t:   float = 0.0          # geometry-layer dataclass unity_route_axis.RouteZone
    end_t:     float = 1.0          # (clamped to [0,1] by a field_validator)
    modifier:  Literal["flat", "ripple", "dip", "rough"] = "flat"
    amplitude: float = 0.0          # clamped >= 0
    frequency: float = 0.0          # clamped >= 0
    layer:     str = ""             # resolver-meaningful label, e.g. "sand", "rock"
    label:     str = ""             # human-readable only, never branched on

class CourseSpec(BaseModel):
    zones: list[RouteZoneSpec] = Field(default_factory=list)
```

Landed as `course: CourseSpec = Field(default_factory=CourseSpec)` on
`WorldSpec` (today's `WorldSpec` also has `regions: list[WorldRegion]` — flat
AABB regions with no parametric-axis concept at all; `course` is the
parametric-axis counterpart). **Not** implemented: the sketch's separate
`axis: Literal["path","depth"]` field and `corridor_half_width` — the axis
turned out to be implicit in which archetype consumes the zones (ArenaPlane
reads `t` as arc-length, BoundedVolume as `tier_of(e)`), so a schema
`axis` enum wasn't needed to make that distinction; `corridor_half_width`
stays a future addition once an archetype actually varies it (today's two
interpreters use each archetype's own existing width/spacing logic).

Step 3 (LLM) fills `zones` from the brief's own course description — **not
yet wired**: nothing prompts the Pipeline LLM to author `RouteZoneSpec`
entries today, so `zones` only gets populated by hand-authored schemas or
tests until step 5 below lands. Step 5 (`unity_layout.py`, this repo's
Step 5 in the pipeline sense) already knows which archetype was selected and
hands the zone list to that archetype's interpreter
(`_layout_arena_plane`/`_layout_bounded_volume`); the interpreter is
deterministic Python, same as every other generator. Nothing here adds an
LLM call to Steps 4-7 — `zones` is schema content the LLM will write once,
like every other field.

For a modifier verb no interpreter has yet (a medium this compiler doesn't
support), the existing `extensions_metadata` sandbox (see
`docs/SCHEMA_EXTENSIONS.md`) is the right escape valve: author it there first,
promote it to a real `RouteZoneSpec.modifier` enum value once it's proven
useful, same "grows in step, together" discipline already used for atom/mode
vocabularies.

## Open questions this plan doesn't resolve

- Whether `depth`/secondary-axis zones need their own `RouteAxis.Sample`
  (e.g., a real underwater course might want depth to vary WITH `t`, not be
  independent of it — a channel that gets deeper toward one end).
- Whether `corridor_half_width` should itself vary by zone (a narrowing
  canyon) — today it's one constant per course.
- How `unity_playability.py` should score a `CourseSpec` for fidelity
  (today's `concept_fidelity` check has no notion of "does this zone list
  actually reflect the brief's named features").
