# Naming audit: `kind` vs. `type`

`kind` and `type` are **both canonical** in this codebase. They are not
duplicate names for one concept — collapsing them (or letting a class grow
both) would erase a real semantic split that resolvers, generators, and
playability checks already depend on.

## The split

- **`kind`** — asset/config **category**: what bucket of thing this is.
  Drives asset resolution, catalog lookup, and dispatch by bucket.
- **`type`** — behavior/action/variant **classification**: what this thing
  does or which variant of a behavior it is.

If a new field is naming "what bucket" -> `kind`. If it's naming "what
behavior/variant" -> `type`. A field that is genuinely both should not
exist on one class — see Enforcement below.

## Enforcement

`tests/test_naming_kind_type_lint.py` runs `src/naming_lint.py`'s AST scan
over every file in `src/` and `cli/` and fails if any single class declares
both `kind` and `type` as its own fields. This is deterministic (pure AST
walk, no imports of the scanned modules) and runs in the normal test suite —
a PR that introduces drift fails CI with the offending file/line/class name,
not a design discussion after the fact.

If a genuinely new concept needs a third name (neither "category" nor
"variant"), don't reach for `kind` or `type` — name it for what it actually
distinguishes (e.g. `role`, `biome`, `medium` are already used elsewhere in
this codebase for exactly that reason) and add it to this audit table in the
same PR.
